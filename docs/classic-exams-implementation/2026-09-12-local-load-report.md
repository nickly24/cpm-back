# Локальная проверка нагрузки и надёжности — 2026-09-12

Результат: заданный функциональный профиль прошёл на **одноразовой локальной MySQL** без потерянных/лишних голосов и ошибок HTTP после исправления обработки исчерпания пула. Это проверка реализации и локального профиля, **не подтверждение production SLA**.

## Окружение и метод

- macOS ARM64, Python 3.13.14, MySQL 8.0.46, Unix socket; `max_allowed_packet=64 MiB`.
- Настоящие MySQL transactions/locks, mysql-connector pool с reset-session, подписанные JWT и Flask test-client dispatch. Не запускались production приложение, WSGI/proxy и сетевой HTTP сервер; production credentials не используются.
- 50 отдельных комиссий по 6 экзаменаторов, 50 синтетических студентов, общий экзамен, 6 основных вопросов. 90 из 300 основных вопросов сначала дают расхождение; 30 замен; 10 попыток переходят к дополнительному вопросу. Ручное обновление по каждому участнику после завершения.
- Основной прогон: не 300 одновременно исполняемых запросов, а 300 идентичностей и пакетная очередь, исполняемая максимум 32 worker threads / 32 DB connections. Отдельно повторён весь профиль с 16 threads / 16 connections.
- Для перегрузки: пакет 300 чтений, максимум 64 исполняемых потока при пуле 32, затем при пуле 16. Не имитируется постоянный polling.
- `pXXMs`: время исполняемого Flask запроса, включая ожидание DB connection. `queuedPXXMs`: дополнительно ожидание в очереди benchmark executor с момента постановки. Сетевые задержки отсутствуют в обеих метриках.

Уменьшение локальной задержки при 16 workers не означает, что этот размер оптимален в production: здесь влияют Python threads, contention и совместное размещение БД с генератором нагрузки.

Проверены SQL-инварианты: 50 завершённых попыток, 340 предъявлений, 2400 голосов, 90 сохранённых спорных раундов и 30 замен. В последнем прогоне дополнительно явно проверены все итоговые rawTotal, roundedTotal и grade. Расхождения и заменённые вопросы не исчезают из истории.

## Длинная история и предельный банк

- 1000 последовательных половинчатых дополнительных раундов, затем разрешающий вопрос: вместе с основным вопросом сохранены 1002 предъявления и 6012 голосов комиссии. Немедленный повтор вопроса запрещён и проверен на каждой итерации.
- Размер сериализованного текущего состояния до/после длинной истории: 2056 → 2065 bytes, всего +9 bytes от длины числовых полей. HTTP response в этом профиле максимум 2104 bytes. История не встраивается целиком в текущий state.
- Банк: ровно 5000 вопросов, ровно 16 777 216 UTF-8 bytes вопрос+ответ. Первый вопрос/ответ имеют по 61 440 bytes. Для этого отдельного профиля случайный выбор принудительно выбирает первый вопрос, чтобы проверить крупный response; остальная логика start/snapshot настоящая.
- Холодное создание snapshot и start: **318.9 ms в последнем прогоне**, подготовка вместе с ensure/6 ready/start — 355.2 ms. Это одно холодное наблюдение в данном прогоне, не статистически достоверный p95 холодных стартов.
- Snapshot создаётся серверным `INSERT … SELECT`: наибольший измеренный параметризованный SQL request в подготовке — около 730 bytes; весь банк не пересылается одним 16 MiB SQL payload через приложение.
- HTTP response выбранного максимального ASCII вопроса/ответа: 124 897 bytes. Это измерение на ASCII, не универсальная верхняя граница JSON: escaping Unicode/управляющих символов увеличивает размер. Рост с историей по-прежнему ограничен структурой current-state DTO.

## Найденные и исправленные проблемы

1. В исходном overload-прогоне 64 threads / 32 connections было 229 HTTP 500 из 300 запросов: mysql-connector немедленно выбрасывает `PoolError` при пустом пуле. Новый домен теперь ожидает освобождения соединения до 500 ms **до начала транзакции**. Если пул всё ещё занят — 503 `exam_temporarily_unavailable` и `Retry-After: 1`. Повторяется только получение connection, не SQL и не mutation. В обоих overload-прогонах после исправления ошибок не было. Отдельные offline tests проверяют ограничение ожидания и единственное начало транзакции после восстановления.
2. Отдельным реальным конкурентным API-тестом проверено создание экзамена двумя одинаковыми запросами с одним ключом. Barrier гарантирует, что оба initial SELECT не находят receipt. После конфликта UNIQUE проигравший запрос перечитывает receipt победителя: ответы 201 + 200/replayed, один exam ID. Полная команда повторно не выполняется.
3. Проверка числа запросов каталога исключает только служебные SET statements; обязательный `STRICT_TRANS_TABLES` не считается N+1. Ограничение числа доменных запросов при 20 студентах сохранено.

## Ограничения допуска

Целевые локальные задержки из FEX-16 выполняются, в том числе с очередью. Однако этот результат не заменяет rehearsal на окружении с production-equivalent CPU/RAM/MySQL version/network RTT, количеством WSGI workers/threads, суммарной ёмкостью пулов и параллельной legacy-нагрузкой. Не проверялись долгий soak, рестарт процесса во время транзакции, отказ сети/БД и одновременная нагрузка импортов/рейтинга. Тесты correctness rollback/idempotency покрываются отдельным пакетом, но не являются отказоустойчивым инфраструктурным стендом.

Подбор production pool должен учитывать общий `max_connections` и число процессов; не переносить локальные 32 connections на каждый worker вслепую. При реальном исчерпании 500 ms допускается контролируемый 503, а не бесконечное ожидание или потеря команды.
