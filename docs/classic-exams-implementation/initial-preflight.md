## Технические корректировки перед продолжением

Это изменения фактического проекта после предыдущей редакции ТЗ, а не выполненная реализация экзаменов.

1. **Нумерация:** migrations/014_admin_roles.sql уже существует. Не переписывать/повторять её. Новый диапазон экзаменов планировать с015; обновить ссылки ТЗ при создании фактических миграций.
2. **Права:** появился staff_admin и admin_role_users. Его id не является admins.id. Сохранить существующие view/edit permissions; новые audit/receipt модели обязаны различать actor role+id. Нельзя допускать staff_admin к записи в FK на admins по совпавшему числу. Общий список направлений также должен учитывать право exams.
3. **MySQL:** version8.0.22-13, legacy PK — signed INT, sql_mode пустой. DDL соединение должно включить строгий session sql_mode и контроль warnings; не менять глобальные настройки сервера.
4. **Размер пакета:** max_allowed_packet=16777216. Лимит банка16MiB плюс JSON/SQL overhead требует отдельной проверки и безопасного решения; не увеличивать глобальный параметр автоматически.
5. **Совместимость:** изменение val DOUBLE→DECIMAL меняет тип Python-значения, а старый Flask JSON может вернуть строку. Сначала подготовить совместимые legacy serializers и исправить int-суммирование дробных баллов.
6. **Удаление пользователей:** текущий код отдельно коммитит удаление credentials до студента. Перед новым RESTRICT нужны атомарность и защита от гонки с назначением.
7. **Classic в старом API:** /get-all-exams уже защищён require_auth, но type guards отсутствуют. Не создавать classic-строки до совместимого чтения/удаления и рейтинга.
8. **Пилот:** examinators пуст. Для голосования нужен реальный отдельный экзаменаторский аккаунт; админом голосовать нельзя. Не создавать сотрудников/учётные записи автоматически в production.
9. **Фронтенд:** API_BASE_URL по умолчанию указывает на prod. Для локальных тестов явно переопределить origin; использовать capabilities gateway и сохранить существующие dirty changes административных прав.
10. **Безопасный выпуск:** порядок «миграция → код» применим только к проверенным additive DDL. Преобразования legacy данных, ограничения и первые classic writes зависят от совместимого backend.
