## Цель

Перенести прохождение теста с фронта (`localStorage`, клиентский scoring, клиентский shuffle) на бэкенд: попытка (`attempt`), таймер, промежуточные ответы, серверная проверка времени и баллов. Фронт — только UI.

---

## 1. Attempt и таймер (бэкенд)

- При **старте** официальной попытки: запись в Mongo `test_attempts` (`studentId`, `testId`, `startedAt`, `expiresAt = startedAt + timeLimitMinutes`, `status: in_progress`).
- Промежуточные ответы: **PATCH** по `questionId`, не в localStorage.
- Перезагрузка / другое устройство: **GET** активной попытки → тот же прогресс и оставшееся время с сервера.
- После `expiresAt`: **не принимать** новые/изменённые ответы; политика финала при timeout — TBD (блок только / авто-submit).
- **Submit** → расчёт баллов **только на бэке** → финальная запись в `test_sessions` (одна на `studentId + testId`).
- Проверки на start/submit: окно `startDate`–`endDate` (Москва), не external, не сдан ранее.
- `POST /create-test-session` для студента: убрать или оставить только внутренним шагом после submit (без доверия `score` из body).

---

## 2. Разделение API: без утечки правильных ответов

| Endpoint | Кто | Содержимое |
|----------|-----|------------|
| `GET /test/<test_id>` | **admin** | Полный тест, включая `isCorrect`, `correctAnswers` |
| Вопросы для сдачи | **student** (владелец attempt) | Через `POST .../start` и/или `GET /test-attempt/<id>` — **без** ключей |
| Просмотр после сдачи | **student** | `stats` / отдельный `review` — что отвечал; разбор правильных — только при `visible` |

Студент **не** использует admin `GET /test/<id>` при прохождении и просмотре своей сдачи.

---

## 3. Порядок вопросов (shuffle на бэке)

### 3.1. Генерация `questionOrder`

- Shuffle **один раз** при `start`, сохранить в attempt: `questionOrder: number[]` (массив `questionId`).
- **Валидация на бэке (обязательно):**
  - длина = числу вопросов в тесте;
  - каждый `questionId` из теста ровно **один раз** (нет дублей, нет лишних/чужих id);
  - при submit сверять, что все ответы ссылаются на id из этого набора.

### 3.2. Отправка ответов

- Клиент шлёт ответ **по `questionId`**, не по индексу на экране (UI может показывать «вопрос 3 из 10», но API — всегда `questionId`).
- Порядок отображения на фронте = `questionOrder` с бэка (фронт **не** перемешивает сам).

---

## 4. Навигация по вопросам во время попытки

### 4.1. Уже отвеченные

- В UI отображаются все вопросы из `questionOrder` (или прогресс-лента / список).
- Вопросы с сохранённым ответом в attempt — **визуально отмечены** (отвечен / текущий / не отвечен).
- Данные для отметок: `GET attempt` → массив `answers` по `questionId`.

### 4.2. Возврат к предыдущим — только просмотр

- Студент **может** перейти к уже отвеченному вопросу и **увидеть**, что он выбрал/написал.
- Студент **не может** изменить ответ на вопрос, который уже зафиксирован в attempt (read-only для «прошлых»).

**Бэкенд:**

- PATCH разрешён только для **текущего** вопроса попытки **или** для вопросов без ответа; для уже сохранённого `questionId` — **403** (или отдельный флаг `locked: true` в GET).
- Альтернатива: хранить `currentQuestionId` / максимальный «закрытый» индекс в `questionOrder` — PATCH только для текущего шага вперёд (линейно). *Уточнить с продуктом: только линейный проход или свободный просмотр назад без правки.*

**Рекомендация под описанное поведение:**

- Свободная навигация **назад** для просмотра.
- PATCH **запрещён**, если для `questionId` уже есть запись в `answers` (immutable после первого сохранения).
- PATCH разрешён для текущего неотвеченного и для «текущего впереди» только один раз при первом ответе.

### 4.3. Истечение времени

- После `expiresAt` — ни PATCH, ни смена «текущего» (кроме submit/просмотра статуса — TBD).

## 5. После сдачи: история «что было на экране»

Чтобы студент (и админ) видел **какие вопросы были в попытке** и **что именно он ответил**:

- В финальной `test_sessions` (или в связанном snapshot в attempt при submit) сохранять:
  - **`questionOrder`** — порядок показа в этой попытке;
  - **`answers`** — с выбранными вариантами / текстом (как сейчас);
  - после scoring — `points`, `isCorrect` per answer (с бэка).
- Endpoint просмотра (`review` / расширенный `stats`):
  - вопросы в порядке **`questionOrder`** той попытки;
  - текст вопроса и варианты **без** ключей до сдачи; **после** сдачи при `visible` — с разбором (что верно/неверно).

Так replay сдачи не зависит от текущего порядка вопросов в редакторе теста (если админ потом переставил вопросы в CRUD).

*Детали UI review — отдельная задача; в бэке заложить сохранение `questionOrder` в финальной сессии.*

## 9. Критерии приёмки (расширенные)

- [ ] `questionOrder` без дублей, валидируется на бэке при start.
- [ ] Ответы только по `questionId`; порядок UI = `questionOrder` с сервера.
- [ ] Отвеченные вопросы видны в навигации; возврат назад — просмотр без изменения.
- [ ] PATCH на уже отвеченный `questionId` отклоняется.
- [ ] После сдачи в сессии есть `questionOrder` + ответы для просмотра «как проходил».
- [ ] Студент не получает правильные ответы до сдачи через admin `GET /test/<id>`.
- [ ] Attempt + таймер + submit scoring на бэке; продолжение с другого устройства.
