# Аудит расчёта тестов и рейтинга — 18.07.2026

## 1. Резюме инцидента

18 июля задача пересчёта рейтинга №38 обработала 335 учеников с результатом
`successful=0`, `failed=335`. У всех учеников одна ошибка:

```text
can't compare offset-naive and offset-aware datetimes
```

Причина: новые даты тестов сохраняются с часовым поясом (`+03:00`), а границы
периода рейтинга создавались без часового пояса. Ошибка возникает в
`calculate_ratings._test_start_in_period()` до расчёта конкретного ученика.

Предыдущая задача №36 от 16 июля прошла успешно: 334/334. Следовательно,
массовое падение — регрессия после перехода тестов на timezone-aware даты.

Последствия тяжелее самой ошибки:

- задача имеет статус `completed`, хотя провалились 335 из 335 учеников;
- перед обработкой `save_all_ratings()` безусловно удаляет весь `Allratings` и
  весь `rate_rec`;
- после задачи №38 в production: `Allratings=0`, `rate_rec=0`;
- исходные результаты не потеряны: MongoDB `test_sessions=4704`, MySQL
  `test_sessions=2280` (результаты внешних тестов).

Локальный фикс нормализует все даты в `Europe/Moscow` и сравнивает календарные
даты. Последнее также исправляет старый дефект: `date_to` ранее означал 00:00,
поэтому тест, начавшийся позже полуночи в последний день периода, исключался.

## 3. Как считается балл теста

Источник истины для новых official attempts — серверный `scoring.py`.

### 3.1. Вопрос с одним вариантом

Полный вес вопроса начисляется, если `selectedAnswer` совпадает с `id` любого
варианта с `isCorrect=true`. Иначе 0. Частичного балла нет.

### 3.2. Вопрос с несколькими вариантами

Полный вес начисляется только при точном равенстве множеств:

```text
selected answer IDs == all correct answer IDs
```

Любой лишний, отсутствующий или неизвестный ID даёт 0. Частичного балла и
штрафа нет. Порядок выбранных ответов не важен, дубли схлопываются через `set`.

Критический крайний случай: если у multiple-вопроса нет ни одного правильного
варианта, пустой ответ равен пустому множеству правильных ответов и получает
полный балл. Поэтому сервер обязан запрещать публикацию такого теста.

### 3.3. Текстовый вопрос

Строка приводится к `strip().lower()` и сравнивается с таким же образом
нормализованным списком `correctAnswers`. Различия регистра и пробелы по краям
игнорируются; внутренние пробелы, `ё/е`, пунктуация и Unicode-нормализация не
игнорируются. Совпадение с любым эталоном даёт полный вес, иначе 0.

### 3.4. Итог теста

```text
earned = сумма points начисленных ответов
maximum = сумма points всех вопросов текущего определения
score = round(earned / maximum * 100, 2)
stored score = int(score)
```

Фактически сохраняется целое число с отбрасыванием дробной части, а не
округлённые сотые. В production 3 848 из 4 704 session имеют математически
дробный процент, который был усечён (например, 82.81 → 82). Это влияет и на
рейтинг, поскольку рейтинг читает сохранённый `session.score`.

Если `maximum=0`, итог равен 0. При этом в production найдено 30 вопросов с
нулевым/некорректным весом, один single-вопрос без правильного ответа и один
тест без вопросов. CRUD `PUT /test/<id>` не выполняет обязательную серверную
валидацию определения, поэтому UI-валидация не защищает API, импорт и старые
данные.

### 3.5. Несколько путей записи результата

- Новый official attempt: сервер валидирует raw answers, считает их и создаёт
  `test_sessions`.
- Practice attempt: использует scoring, но не создаёт official session и не
  влияет на рейтинг.
- Legacy `/create-test-session`: для ученика закрыт кодом 410, но admin может
  передать готовые `answers` и произвольный `score`; сервер их не пересчитывает.
- Forced submit: серверный scoring.
- Перерасчёт после редактирования: серверный scoring по текущему тесту, но с
  отдельным алгоритмом построения порядка ответов.

Следствие: «единая формула» есть, но единого защищённого write-path пока нет.

## 4. Как тесты входят в рейтинг

Для каждого ученика `calculate_tests_rating()` загружает все его Mongo sessions,
все Mongo tests и внутренние/внешние тесты MySQL за период.

### 4.1. Внутренний тест считается eligible, если

- `published` не равен `false`;
- `isActive` не равен `false`;
- календарная дата `startDate` попадает в `[date_from, date_to]`.

`visible`, `endDate`, наличие/статус попытки и фактическое наступление времени
старта внутри текущего дня не учитываются. Отсутствующая/невалидная `startDate`
полностью исключает тест. Если eligible-тест не сдан, ученику ставится 0.

Риски текущего правила:

- тест, который стартует вечером сегодня, уже даёт 0 утром сегодня;
- тест с прошедшим `startDate`, но ещё открытым `endDate`, уже штрафует
  не сдавших;
- снятие `published` задним числом исключает тест из рейтинга всех учеников;
- `visible` управляет показом ответов, но не рейтингом — это логично, однако
  названия полей/переключателей легко перепутать;
- изменение `startDate` или направления ретроактивно переносит вклад теста.

### 4.2. Внешний тест

Все `tests_out.date` в периоде входят в рейтинг. Нет `test_sessions.rate` — 0.

### 4.3. Направления и общий балл тестов

По каждому направлению считается простое среднее его тестов. После решения от
18.07.2026 общий `tests.rating` считается как среднее этих средних направлений.
Поэтому каждое направление с тестами за период имеет одинаковый вес независимо
от количества тестов внутри него. Направление без единого теста за период не
создаёт bucket и не участвует в знаменателе. Если тесты в направлении были, но
ученик их не сдавал, они дают 0 и направление участвует.

Пример:

```text
Направление A: 10 тестов по 100
Направление B: 1 тест на 0
direction averages: A=100, B=0
tests.rating = (100 + 0) / 2 = 50
```

В рейтинговом отчёте тесты сгруппированы по направлению: первым столбцом блока
показывается его среднее, затем результаты конкретных тестов этого направления.

### 4.4. Финальный рейтинг

```text
homework component = average homework score * 0.25
exam component     = average exam points * 6
tests component    = average test percent * 0.45
final              = сумма компонентов
```

Формула предполагает ДЗ и тесты в шкале 0–100, экзамен в шкале 0–5. Сервер не
проверяет эти диапазоны. Пропущенные ОВ, экзамены и eligible-тесты входят как 0.

## 5. Что происходит при изменении теста

`PUT /test/<id>` сначала записывает изменение, затем в том же HTTP-запросе
синхронно вызывает `recalc_test_sessions(test_id)`. Ответ клиенту ждёт полного
прохода по всем сдачам теста.

Глобальный рейтинг при этом автоматически **не** пересчитывается. Он остаётся
устаревшим до ручного запуска `/calculate-all-ratings`.

Текущий frontend основного редактора не отправляет PUT на каждый символ:

- существующий тест требует явного подтверждённого сохранения;
- draft autosave через 800 мс пишет только `test_drafts` и не пересчитывает
  session/rating;
- старый form тоже пишет тест только по submit.

Но любое фактическое PUT пересчитывает все session, даже если изменены только
`published`, `visible`, заголовок, направление, даты, лимит времени или canvas.
Переключатели списка используют частичный PUT, поэтому один клик действительно
запускает полный rescoring сдач выбранного теста.

### 5.1. Матрица изменений

| Изменение | Текущий эффект session | Нужен rescoring? | Эффект рейтинга |
|---|---|---|---|
| title | обновляется title и пересчитываются все ответы | нет | только detail title |
| direction | полный rescoring | нет | тест переносится между направлениями |
| startDate | полный rescoring | нет | тест входит/выходит из периода |
| endDate/time limit | полный rescoring | нет | сейчас rating не меняется |
| published/isActive | полный rescoring | нет | тест входит/выходит из rating |
| visible | полный rescoring | нет | rating не меняется |
| canvas/layout | полный rescoring | нет | rating не меняется |
| текст single/multiple-вопроса | полный rescoring | нет | не должен меняться |
| текст варианта | полный rescoring | нет, ID не изменился | не должен меняться |
| points вопроса | полный rescoring | да | меняются numerator/denominator |
| isCorrect | полный rescoring | да | меняется правильность прошлых ответов |
| correctAnswers текста | полный rescoring | да | меняется правильность |
| добавить вопрос | старым session добавляется unanswered=0 | да по текущей политике | обычно снижает балл |
| удалить вопрос | старый ответ удаляется | да | меняются numerator/denominator |
| изменить questionId | выглядит как delete+add | да | старый ответ теряется |
| добавить correct option в multiple | старый неполный набор становится 0 | да | баллы могут снизиться |
| добавить incorrect option | полный rescoring без изменения формулы | нет | не должен меняться |
| удалить выбранный option | выбранный ID становится неизвестным → 0 | да | балл может снизиться |
| сменить тип вопроса | старый answer.type имеет приоритет над новым type | да, но текущий результат недостоверен | непредсказуемо |
| reorder вопросов | ответы остаются в legacy-порядке | scoring нет | score не меняется, review может |

### 5.2. Версии против ретроактивного перерасчёта

Новые schema-v2 attempts фиксируют `testVersionId` и считаются по неизменяемой
версии. Но последующий `recalc_test_sessions()` игнорирует `testVersionId` и
переписывает `answers`, `score` и title по текущему тесту. При этом не обновляет
`testVersionId` и `finalSnapshotHash`.

Итог: immutable evidence и сохранённый результат начинают противоречить друг
другу. Это фундаментальный конфликт политик. Нужно выбрать и закрепить одну:

1. **Историческая честность (рекомендуется):** завершённая session неизменяема;
   исправление ключа ответа создаёт correction/version и явно пересчитывает
   только затронутые результаты с audit trail.
2. **Всегда текущий ключ:** session — производная от raw answer и текущей версии;
   тогда version/hash должны обновляться вместе, а старый результат храниться
   отдельной ревизией.

Сейчас система пытается одновременно применять обе политики.

## 6. Глобальный перерасчёт рейтинга

### 6.1. Текущий алгоритм

1. Удалить все строки `Allratings` и документы `rate_rec`.
2. Загрузить всех учеников.
3. Для каждого ученика отдельно рассчитать homework, exams, internal/external
   tests.
4. Upsert агрегата в MySQL и detail в MongoDB.
5. Каждые три ученика открыть отдельное соединение и обновить progress job.

На одного ученика приходится примерно:

- 5+ read-запросов MySQL до сохранения;
- 2 Mongo query, включая повторное чтение **всех tests**;
- отдельные MySQL SELECT + UPDATE/INSERT для `Allratings`;
- Mongo find + update/insert для `rate_rec`;
- отдельные commit на ученика;
- повторная проверка существования уже выбранного из `students` ученика.

Для 335 учеников это тысячи round trips и многократное чтение одинаковых
справочников/тестов. Это не связано с каждым кликом редактора, но глобальная job
действительно масштабируется как `students × data queries`.

### 6.2. Дефекты надёжности

1. **P0: destructive clear before validation.** Любая общая ошибка оставляет
   рейтинг пустым.
2. **P0: нет атомарной публикации между MySQL и MongoDB.** Возможны агрегат без
   detail или detail старого периода.
3. **P0: status `completed` при per-student failures.** Даже 0/335 считается
   completed; UI вводит администратора в заблуждение.
4. **P1: process-local daemon thread.** Перезапуск убивает job; несколько
   gunicorn workers имеют разные `_active_recalc_job_id`.
5. **P1: race в create job.** `has_active` и INSERT не атомарны; два workers
   могут одновременно создать job.
6. **P1: period не является частью ключа `Allratings`.** Хранится только один
   «последний» рейтинг, а `rate_rec` перезаписывается по rating_id.
7. **P1: UTC/Moscow несогласованность журнала.** `created_at/started_at` пишет
   MySQL local time, `completed_at` — `datetime.utcnow()`, поэтому completion в
   журнале визуально на три часа раньше старта.
8. **P2: errors JSON разрастается одинаковой ошибкой на каждого ученика.** Нужна
   группировка по signature + несколько sample IDs.
9. **P2: нет dry-run/preflight.** Общая ошибка выявляется только после clear.

## 7. Приоритет найденных проблем

### P0 — немедленно

- timezone regression и неполный `date_to` — локально исправлены;
- production rating сейчас пуст и требует восстановления после deploy;
- убрать destructive clear либо публиковать результат через staging/swap;
- считать job failed, если `failed>0`, и отдельно поддержать `partial` при
  необходимости;
- запретить PUT/publish невалидного определения теста на backend.

### P1 — ближайшая итерация

- разделить metadata update, content revision и answer-key correction;
- не rescoring-ить session при metadata-only PUT;
- вынести rescoring из request в idempotent job с coalescing/debounce по testId;
- определить политику immutable session vs retroactive correction;
- хранить дробный score (`Decimal128`/число с двумя знаками), не `int`;
- не доверять admin legacy `score` и `points/isCorrect` без явного import mode;
- считать рейтинг set-based/batch, предварительно загрузив tests/directions;
- обеспечить единственный durable worker/lease, retries и restart recovery.

### P2 — качество модели

- закрепить равный вес направлений в бизнес-документации и API-контракте;
- утвердить момент штрафа за пропуск: startDate, endDate или закрытие attempt;
- валидировать шкалы ДЗ/экзамена/теста;
- Unicode-нормализация и политика текстовых ответов;
- уникальные стабильные IDs вопросов/вариантов, не перенумерация по позиции;
- versioned rating periods и история публикаций.

## 8. Рекомендуемая целевая схема

### 8.1. Сохранение теста

1. Клиент сохраняет draft сколько угодно часто — без влияния на результаты.
2. Publish создаёт immutable `test_revision` после backend validation.
3. Сервер вычисляет diff по семантическим категориям:
   `metadata`, `content`, `answer_key`, `weights`, `eligibility`.
4. Metadata/content без изменения ключа не rescoring-ят ответы.
5. Answer-key/weights создают одну coalesced job на `testId + revisionId`.
6. Job читает raw immutable answers, пишет новую result revision и audit diff.
7. После успеха invalidates только затронутые rating aggregates.

### 8.2. Рейтинг

1. Preload периода: students, tests, directions, homework, exams, sessions.
2. Рассчитать новый snapshot в staging с `calculation_id` и `period_id`.
3. Проверить invariants: число учеников, диапазоны, failures=0, totals.
4. Атомарно переключить `current_calculation_id`.
5. Старый snapshot сохранить для rollback и сравнения.

Это превращает публикацию из «стереть старое и надеяться» в «сначала полностью
построить новое, затем одним переключением опубликовать».

## 9. Обязательная матрица тестирования

### Scoring

- single: correct, incorrect, unknown, null, duplicate correct options;
- multiple: exact, missing, extra, duplicate selection, unknown option, zero
  correct options;
- text: case, outer/internal spaces, empty references, Unicode;
- weighted totals, zero total, fractional percent and boundary 0/100;
- invalid/duplicate question and option IDs.

### Recalculation diff

- каждый тип изменения из таблицы 5.1;
- несколько последовательных сохранений coalesce в одну job;
- повторный запуск той же job idempotent;
- edit во время active legacy/v2 attempt;
- сохранённые version/hash/result остаются согласованными;
- удаление вопроса/варианта не теряет raw historical evidence.

### Rating

- internal/external, сдан/пропущен;
- published/isActive/visible/start/end на границах периода и часовых поясов;
- несколько направлений с разным числом тестов;
- partial failures, Mongo/MySQL failure, worker restart, concurrent start;
- старый snapshot доступен до успешной публикации нового;
- job status соответствует фактическому результату.

## 10. Безопасное восстановление текущего production

1. Deploy timezone/date-range fix.
2. До job сохранить backup/export текущих `test_sessions`, `tests` и job log;
   `Allratings/rate_rec` уже пусты.
3. Выполнить read-only dry-run хотя бы для одного ученика и сверить eligible
   tests/expected components.
4. Запустить полный рейтинг за нужный период один раз.
5. Проверить: `successful=335`, `failed=0`, `Allratings=335`, `rate_rec=335`,
   отсутствие NaN/out-of-range и совпадение нескольких учеников с ручным
   расчётом.
6. Только после проверки считать рейтинг восстановленным.

До реализации staging/swap следующий глобальный запуск остаётся потенциально
destructive при любой новой общей ошибке.
